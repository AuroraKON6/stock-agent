## 4. 行为设计（与缺陷的对应）

### F01 输入版本单一事实源

- `create_task`：从 payload 读取一次 `input_version`（正整数校验，拒绝 bool/0/字符串），**写列**，并把同值注入 payload 投影；默认缺省为 1。
- `record_human_response(provide_input)`：新版本 = 列+1；payload 同步为新版本；同一事务写入 `task_input_snapshots`（task_id, version, canonical JSON, sha256, actor, reason）。快照按 (task, version) 主键不可变，重写即 `TaskRuntimeError`。
- `dify_api` 两处独立读 payload 版本的位置（`_public_task_view`、`submit_candidate_result`）改为读列。
- 历史分歧：新增只读 `input_version_divergence_report()`，报告列/payload 不一致的行并给出**候选**映射（payload>列时建议以 payload 为候选权威），明确"需人工复核、不自动修史"。测试用手工插入的 F01 形态遗留行验证报告命中且零写入。

### F03 业务意图与平台 run 分离

- 新列 `business_intent_id`（部分唯一索引，空串豁免以兼容旧行）+ 新表 `task_platform_runs`（run_key=platform::run_id 主键）。
- `create_task(business_intent_id=..., platform_run=...)`：**意图优先去重**——同意图要求 execution_mode 一致且逻辑内容指纹相等；逻辑指纹剔除 origin 中的平台 run 标识（dify_run_id 等），平台重试不是新内容。意图命中即复用任务并把本次 run 记为关联行；同 run 绑不同任务 → 冲突。
- 旧库迁移：`_migrate_legacy_schema()` 增量 `ALTER TABLE` 加列 + 建部分索引；旧行不回填、不改写。测试用真实 v1.0 形态的旧 schema 验证迁移后可继续写入。
- Dify 网关：未显式传意图时从**业务内容**（case/问题/版本/流程/提示词/模式）派生稳定 `dify-bi-*` 意图——绝不含 `dify_run_id`；响应新增 `business_intent_id` 与 `platform_run`（association_outcome 按该 run 是否已关联判定）。
- 幂等键兜底：显式 key 冲突、默认 key 行为、event/question 的"重建上下文不算新请求"豁免全部保留（既有测试不改一字通过）。

### F05 worker 返回持久真实状态

- `_fail/_blocked/_renew_or_fail/awaiting_human/complete` 五个出口全部改为返回 `TaskStore` 持久化后的实际 status（requeue → `queued`；取消 → `cancelled`；终态 → `failed/blocked/succeeded`），不再硬编码。
- `run_daily_task_cycle`：worker 返回 `queued` 计入 `retried`，不再混入 `failed`。

### F21 问题意图区分

- `ensure_question_task(intent_id=...)`：网络/提交重试——同意图同内容去重，异内容冲突。
- `ensure_question_task(new_research=True[, as_of=...])`：铸造全新 `qi_*` 意图，记录 as-of，`origin.prior_task_id` 关联同问题旧任务；旧任务终态不被重开。
- 默认路径：原稳定问题键行为不变（CLI 与既有调用零改动）。
