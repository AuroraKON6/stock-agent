```text

        |

        |
        v
Dify 研究流程：分支、分析步骤、等待补证
        |
        v

  |-- 获准数据与事实快照
  |-- 模型调用治理、预算与尝试回执
  |-- 证据绑定、结果校验和任务状态
        |
```

Dify 可以保存自己的运行记录；业务案件是否完成、取消、等待人或已签收，只由 Python 的权威状态机判断。
关联 `case_id / task_id / input_version / attempt_id / dify_run_id / workflow_version`，不把某个节点绿色当作案件批准。

## 两阶段迁移

### 第一阶段：Dify 编排现有能力

第一条流程选“单标的公开事件研究”，不是全市场监控，也不是直接搭八个 Agent。

1. 从经认证的业务入口接收标的和问题，后端进行请求分类、权限检查和幂等创建。
2. Dify 使用受限服务凭据调用后端接口；凭据的用途不能由模型参数扩大。
3. 后端在已有治理与预算下执行研究，过渡期复用 Pi。
4. 长任务返回任务 ID；Dify 做有次数/总时长上限的查询，未完成时返回案件入口，不无限占用流程或盲目重提任务。
5. 获取研究草稿、证据引用、未知项与补充问题。先用确定性模板展示，不再额外调用一个模型“美化”同一结果。
6. 用户在已验收的业务身份入口提交追问/补证，产生新输入版本，再启动一次受控研究。
7. 签收、否定与版本冲突由后端处理，Dify 获得处置结果。

第一阶段验收证明的是 Dify 接线与交互，不宣称已经迁移 AI 推理运行时。它应是有明确退出条件的过渡，而不是永久增加一个空壳。

### 第二阶段：逐模块迁移 AI 研究步骤

先迁移一个“业绩点评草稿”模块。Dify 使用获准事实包执行研究步骤，Pi 对同一任务的执行入口关闭；不能双跑然后把重复费用隐藏为测试。

每个模型请求必须经过受控模型调用边界，完成输入治理、原子预算、调用身份、请求/实际模型记录和输出引用验证。只在流程开始检查一次不够。
可采用 Python 托管的研究步骤 API；若使用 Dify 原生 LLM/Agent 节点，则先实现并验证强制受控的模型代理或等价机制，禁止节点凭独立 provider key 绕过预算与外发审查。

模型和工具的自动重试都应由一个明确层负责；平台隐式重试也必须计入预算。请求已发出但结果未知时保留 unknown，不自动释放额度并重发。
Dify 可视化修改提示词后，必须发布为新的候选流程版本并重新评测；不能把生产提示词编辑变成免审的热更新。
模块通过对照验收后切换，保留旧版本回滚能力。Pi 只在确有未迁移职责时保留，不作为重复执行链。

## 最小接口契约

优先复用现有接口，不先新建一套 REST 框架。下列名称仅表示职责，不是已经存在的端点：

- 创建研究：输入研究范围、输入版本与幂等键；返回 task_id 和状态，不同步等待整轮模型完成。
- 查询研究：只返回该调用主体获准查看的任务状态、公开最小化草稿和引用。
- 读取事实包：返回冻结版本和可引用集合；内部名册、限制名单、原始身份文件、密钥及非获准正文不进入 Dify。
- 提交研究候选结果：绑定当前 attempt、流程版本与输入哈希；校验引用和 fencing 后提交，拒绝旧结果覆盖。
- 提交反馈/取消：必须有经过验证的用户主体、command_id 和 expected_version，不能仅接受 Dify 传来的 actor 字符串。

服务认证与真人授权分离。Dify 的 app key、API user 字段、表单填写者名字都不能直接作为本项目的批准身份。
首版 Dify 可展示待补证表单或业务页面链接，但未经身份绑定验证的表单回复只能作为待核实输入，不能触发受保护审批。

## 部署与安全边界

- 默认设计为隔离的本地/自托管开发实例；不自动上传现有数据到 Dify Cloud。
- DF-01 先检查实际 Docker/WSL/端口/磁盘条件，不预设已安装；本次选型不代表已授权安装系统组件、开放公网或启用自启动。
- 固定版本与镜像摘要，核查插件和依赖；不使用浮动 latest 作为生产基线，不整包安装金融 MCP/skills。
- 开发实例使用专用存储和测试账号，不挂载真实 data、Vault、用户 HOME、Docker socket 或全盘；容器不是自动安全保证。
- Dify 只能访问后端白名单能力，不能通过 HTTP/代码/插件节点任意访问互联网或扫描内网；内部 API 在明确隔离网络中精确放行，不能关闭全局 SSRF 防护。
- 只给 Dify 最小服务凭据，不给 Kimi/DeepSeek 的共享桌面凭据；秘密不进 DSL、Git、截图或提示词。
- Dify 执行日志、文件和备份同样纳入数据权限与留存策略；配置容量上限和脱敏，不清理业务审计账本来腾空间。
- 禁止自动交易、自动供应商批准、修改生产 skills lock、恢复计划任务或擅自修改主模型。

## 必须做的负向验收

1. 同一输入被重复点击、平台自动重试、回调重复到达：只有一个逻辑任务，没有额外收费请求。
2. Dify 重启或后端超时：已有业务任务仍可查，不因流程失败重跑整轮。
3. 案件取消或换版后旧结果到达：不能覆盖当前状态。
4. 越权 task_id、伪造 actor、陈旧批准链接：后端拒绝，不依赖前端隐藏按钮。
5. 插件/模型节点绕过受控 API：出站或凭据边界阻断，而不是仅靠提示词约束。
6. 预算耗尽、429、401、未知请求结局：分类明确、有限重试，实际次数可对账。
7. 事实包被撤销、引用不在投递集合、正文不允许外发：阻断，不能由 Dify 缓存继续使用。
8. 导出的流程含秘密、未批准插件、任意 shell/路径/URL：发布检查失败。
9. 关键数据源失败：能说明缺口并等待补证，不生成无依据的完整研究结论。
10. 从候选 Dify 路径回退：同一任务不被 Pi 再次执行，历史运行和人工反馈仍可追溯。

Python 离线测试仍在项目根使用 `.\.venv312\Scripts\python.exe -B scripts/run_isolated_tests.py`；不得关闭守卫。
Dify 服务/容器和原生进程验收独立准备，不能混入离线测试；浏览器使用临时工作区，不拿正式案件试表单。
技术测试、真实模型、真人反馈、业务启用分别报告，不以节点成功或整张图跑完替代验收。
